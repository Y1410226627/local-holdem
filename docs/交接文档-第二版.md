## 4. 测量方法（这一节比所有代码都重要）

### 4.1 唯一可信的度量：同 seed 配对差分

同一批 seed 跑两臂（开/关某个开关），**逐手相减**再求均值与 CI。配对把公共方差消掉：

| 度量 | 标准差 |
|---|---|
| 单臂每手（绝对水平） | **18.34 BB** |
| 配对差分（同 seed） | 1.2 ~ 9.3 BB |

### 4.2 样本量表（必须记住）

以 sd = 18.34 BB/手 计算，单臂 95% CI 半宽：

| 想分辨的差异 | 需要手数/臂 |
|---:|---:|
| ±50 BB/100 | 5.2 千 |
| ±30 BB/100 | 1.43 万 |
| ±20 BB/100 | 3.23 万 |
| ±10 BB/100 | 12.9 万 |
| 80% 功效检出 **+20** | **13 万** |

**结论：任何「挑战档领先 X 分」的绝对陈述，在万手以内都不要说。**

### 4.4 五个陷阱（我全踩过，都有代价）

1. **测量期间改代码** → 数据里混进代码漂移。我犯过两次，其中一次导致同一份代码测出 +60.4 和 −17.5。**跑批开始后到结束，任何人不得写 `src/` 与 `scripts/`，并记录 `git rev-parse HEAD`。**
2. **样本不独立** → 合并多组前必须查 seed 是否重复。实例：`session-h2h.ts` 的 seed 曾不含 `ARCH`，assign 与 fixed 是同一副牌重跑，合并时 CI 被虚缩 √2（把 n=2000 当成 4000）。
3. **描述性分桶 ≠ 因果** → 诊断显示「跟注收尾 −7.9 BB/手，弃牌 −2.2」，据此收紧跟注，实测 **−3.3**。原因是能跟的牌正是「弃了更亏」的牌，两组比的是不同的牌。**分桶只能提假设，判因果只能靠 A/B。**
4. **离线指标 ≠ 实战** → 蓝图可利用度 2.2320 → 0.0029，实战 +0.9。因为对手是固定启发式，不是最佳回应者，**越接近均衡越放弃剥削**。
5. **计数器要先验证** → 我曾从「hits 恒为 0」推出「专家档没有可剥削的弃牌漏洞」，实际是我读了一个不存在的字段（`r.reasoning`，真实路径是 `r.debug.reasoning`）。**任何统计量在用于结论前，先用已知会触发的场景验一次。**

## 6. 现在已知的能力边界

### 6.1 钱的结构（来自 `diag-street-ev.ts`，3,000 手，描述性）

| 分桶 | 样本 | 均值（BB/手） |
|---|---:|---:|
| 翻前就结束 | 1,968 | **+0.2** |
| 摊牌 | 577 | **−4.7** |
| 巨池（≥100BB 全下） | 338 | **−6.5** |

**翻前是赚的，亏损集中在摊牌与大底池。**

### 6.2 摊牌质量

577 次摊牌，胜率 **44.0%**，赢时 +32.8 BB / 输时 −34.2 BB，**赢输比 0.96**。摊牌牌型：一对 257 次胜率 36%、高牌 114 次胜率 18%。→ 我们**用边缘牌跟到底**。

### 6.3 尺度维度已饱和

翻牌层/转牌层赚的是「该缩的时候缩」。把下注上限从 1.0 池放到 1.35 池，实测 +0.6（上界 +3.1）→ **「放大」本身不产生收益**。

### 6.4 对手没有易取的低级漏洞

翻前读人层要求 `avgFoldToBet ≥ 0.63` 才触发，专家档稳定在 0.28~0.42（平衡带内），所以 **2000 次决策 0 触发**。要靠「对手犯低级错误」提分，在这个对手身上不成立。

## 7. 下一步：三条路

### 路 A（唯一可能带来量级提升）：真子博弈求解器

现状是「纹理代理 + 启发式 + 一个单街河牌求解器」。翻牌/转牌没有真正的求解。

- 需要：抽象（牌面聚类 + 手牌分桶）、剪枝、迭代预算控制；
- 硬指标：**单次决策耗时不能超过现在的量级**（当前平均决策约 121ms），否则 UI 会卡；
- 成本：**以周为单位**，不是一次会话能完成；
- 验收：只能靠 §4.1 的配对差分，且每加一层都要独立 A/B。

### 路 B：换度量，先解决「测不出来」

如果目标是「让人类打不过」，那 **vs 专家档的 BB/100 本来就是错的指标**（专家是固定启发式）。可考虑：

- 用 `scripts/hlb-bots.ts` 的脚本对手做固定基准（方差更低）；
- 或直接用人类对局数据（项目里有 HLB 实测：−98 BB/100，前 2,500 手）。

**先解决度量，再谈提升**——否则每一次改动都只能得到「噪声里看不出来」。

### 路 C：收口

把已到手的 +12.8、四个 bug 修复、测量纪律整理干净，把「挑战档比专家档强多少」诚实地写成「无法在可行样本量下判定」。

### 我的建议

**先 B 后 A**。理由：现在所有实验的失败都可能有两种解释（真的没用 / 测不出来），在换到低方差度量之前，继续改策略是在盲打。

## 8. 需求方定的纪律（硬要求，不可协商）

以下几条**不是建议，是需求方在协作过程中明确要求过的**。我已经违反过其中若干条，代价写在括号里。接手的 AI 请当成项目宪法对待。

### 8.1 后台任务必须实时输出进度

> 需求方原话：**「后续请你后台跑每个任务时都要让任务实时输出进度！」**

- 任何后台跑批，**不允许静默执行**。必须挂一个打印循环，每 **20 秒**输出一行，格式：
  ```
  [01:30:28] arm=1 进度 470/15200 (3%)
  ```
- 进度行要含**时间、当前计数、总数、百分比**；多臂跑批要标出是哪一臂。
- 原因：本环境后台任务约 **18 分钟**被 SIGTERM，没有进度就无法判断是"慢"还是"死了"，也无法断点续跑。
- 反面教材：我早期跑 15,200 局的批，只留最后一行结果，中途被杀了两次都不知道停在哪。

### 8.2 数字说话，不美化、不取整

> 需求方原话：**「不要取整、不要美化」**（原话针对文档改写，但适用于一切报数）

- 报数用**实测原值**，保留工具输出的精度（如 `+6.8`、`−0.1`、`2.2320 → 0.0029`）。
- 禁止用"大约""接近""大概翻倍"替代具体数字。
- 禁止把多个数字"合并"成一个好看的数（例如把四组会话硬平均成 4,000 手）。
- 如果某数是估算、推算或口径不同，**必须当场标注**（例：`+20 BB/100` 是描述性换算，非因果）。

### 8.3 不允许把噪声当结论

- 任何结论必须带 **95% CI 与样本量**；CI 跨 0 就说"看不出"，不要写"有提升趋势"。
- 三态判定沿用项目既有规矩：**Δ ≥ +15 且 CI 下界 > 0 → 采纳；CI 上界 < +10 → 关闭；其余追加样本**。
- 我违反过一次：把 +29.1 当成"水平"汇报，后来发现同一份代码在别的段能测出 −17.5。

### 8.4 不许顺着说"对"

- 需求方会追问确认性细节（例如"也就是说你全都没动对吧"）。此时必须给出**精确到项的数字**。
- **如果实际情况与需求方的理解有偏差，主动纠正**，不要为了顺着对话而附和。
- 我违反过一次：需求方问"是不是没路可走了"，我当时答得过于乐观；真实情况是"便宜的路走完了，但大工程没动"，两者要分清。

### 8.5 先验作用面，再谈收益

- **写代码之前**先估这个改动会命中多少决策。触发率 < 5% 的改动直接不做。
- 反面教材：我为"SB 跛入被加注"写了 40 行，实测 **15,200 局触发 0 次**——该场合根本不发生。

### 8.6 测量纪律（三条铁律）

1. **测量期间代码冻结**：跑批开始到结束，任何人不得修改 `src/`、`scripts/`；跑批前后各记一次 `git rev-parse HEAD` 与 `git status`（应为空）。
2. **一次只测一个变量**：两处改动同时上线，等于两个都无法归因。
3. **seed 独立性与留出段台账**：合并多组前必须查 seed 重复；用过的 seed 段写进 §4.3 台账，新改动一律取未分配区间。

### 8.7 交付前不得宣称"已完成"

- 宣称"做完了"必须同时具备三项证据：`npx tsc --noEmit` 无输出、`npm test` 全绿、以及**该改动自己的实测数字**。
