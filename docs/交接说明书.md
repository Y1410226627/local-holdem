#### 1.4.2 这次事故的三条教训

**教训一：判定「倒退」之前，先验证测量口径。**

T2 到 T6 我浪费了大量时间在「修 AI」，但 AI 没问题，是**尺子**有问题。
从那以后我形成了一个习惯：**任何「A 比 B 差」的结论，先问三个问题**——
同 seed 吗？同参数吗？测量工具本身有没有前提假设被破坏？

`session.ts` 和 `_cmp.ts` 的差别只有一个：桌子是不是每手重建。
但就是这个差别，让「读人能力」这项能力在测量里**整段消失**。

**教训二：合成对手测不出「整体退化」，必须用老版本当对照物。**

跟注站 / 弃牌怪 / 全下怪是三个极端打法，只能回答「对极端打法够不够狠」。
一个版本可能在三个极端对手上都赢，却在正常对局里全面退化——
因为这三个对手加起来也覆盖不了真实牌局的决策分布。

**老版本是唯一不可替代的对照物**：它代表「上一版真实的整体水平」。
所以每次发版都必须跑 `head2head`（新旧直接对打），不能只跑固定对手。

**教训三：确认倒退之后，必须修到「追平并超过」，不允许用「差不多」糊过去。**

你的原话是「至少持平」「全面吊打」，不是「接近」。这条后来变成了量化门槛：
点估计变差**不允许合并**，必须修或明确回滚。

#### 1.4.3 现在的防复发机制

写进了 `AGENTS.md` 的**第 0 条（最高优先级）**：

1. 任何改动交付前必须跑「对上一个版本」的对照；

5. 无法证明不弱的特性**默认关闭**（翻牌蓝图就是这么被关掉的）。

因为**「倒退」往往是渐进的**：单次改动只掉 3~5 BB/100，CI 完全看不出来，

## 2. 我接手时项目的真实状态（审计结论）

**接手时间**：2026-11-06，版本 v0.14.0（提交 `6fe2bcf`）。
**接手原因**：你怀疑上一个 AI「执行不力」。

审计后确认的核心问题：

### 2.1 挑战宗师是死代码【实测】

`src/ai/aiPlayer.ts` 的 `pickChallengeDecision()` 里写着：

```ts
finalDecision = expertDecision.action;   // 整条挑战分支最后被覆盖
```

也就是说整个「挑战宗师」的决策链算完之后，**结果被专家档的决策覆盖掉**。
挑战档 = 专家档，一行不差。这解释了为什么 `v0.12.2` 的基准里挑战档是 −33.1 BB/100。

### 2.2 翻前强度用 Chen 公式排序，违反「压制」关系【实测】

`preflopStrength` 按 Chen 公式排序，导致 **J9o(0.787) 排在 Q9o(0.647) 前面**。
但 Q9o 在数学上完全压制 J9o（Q>J，9=9）——任何合理的强度指标都不允许这样。
修成按真实胜率排序后：J9o → 0.615，Q9o → 0.686。

### 2.3 翻前跟注完全不看底池赔率【实测】

`ctx.potOdds` 在翻前**一次都没被读过**。面对「加注到 40」和「全下 2520」用的是同一个跟注范围。

真实对局里出现过：6 人桌有人 126BB 全下，机器人拿 J9o 跟了 2430，
底池赔率需要 48.2%，而 J9o 对全下范围只有约 30%。

### 2.4 全下动作不计入攻击性统计【实测】

`stateMachine.ts` 的统计里 `allin` 既不算 raise 也不算 call，
于是「每手都全下」的对手 `aggression` 恒为 0，被判定成**最被动的人**，
针对它的剥削逻辑全部失效。

### 2.5 其他

- 范围缓存键只用了「动作个数」，两条不同但长度相同的动作线会撞车；
- `sampleRange` 的强制包含权重写成 `1`，归一化后一手牌吃掉整个范围；
- 求解器的 `rootValue` 在 CFR 迭代**之前**计算，用的是空平均策略（等于均匀随机）。

## 3. 我接手后做了什么（按版本，全部可复现）

从 v0.15.0 到 v0.25.0 共 **33 个提交**，源码从接手时的规模增长到 **26,396 行**（含测试）。

### 3.1 算法层：真 CFR+（v0.15.0）

- 新建 `src/ai/solver/cfr.ts`：遗憾匹配+（regret matching plus）、线性加权平均策略；
- `subgame.ts`：河牌单街子博弈，按 `cpp-cfr` 仓库 `Trainer.cpp:382-391` 的更新式实现；
- 配对基准：同 seed 轮转座位，输出 95% CI（旧基准两种模式用不同 seed，不是配对）。

**关键教训**：v0.15.0 报的可利用度是用**错误的「最佳回应」**算出来的——
按 (SB桶, BB桶) 组合分别取 max，等于让回应方看穿对手手牌，
于是可利用度卡在 **3.3 BB/手**、加迭代也不降。v0.16.0 修掉后降到 0.0176，
当前蓝图是 **0.0167**（24 桶 / 40000 迭代）。**这个 bug 在 v0.15.0 交付时没被发现。**

### 3.2 翻前蓝图重做（v0.16.0）

修掉三个真 bug：
1. 跛入后弃牌的亏损写成 −0.5（应为 −1），把跛入成本砍半 → 这是「SB 99% 跛入」的直接原因；
2. 分桶按「攒够 target 进位」，误差累积导致最后一个桶为空；
3. 最佳回应按组合分别取 max（见上）。

修完后 SB 策略正常：弃 15% / 跛入 36% / 加注 48%。**可利用度 0.0167 BB/手【实测】**。

### 3.3 转牌+河牌联合子博弈（v0.17.0）

`subgameTurn.ts`：转牌 + 河牌两街联合求解，**不需要价值函数**。
这是目前挑战档最实在的一块能力。

**踩过的坑**：`rootValue` 在 CFR 循环之前计算，等于用空平均策略（均匀随机）算价值，
所有 EV 都是负的。移到循环之后才正常：空气牌 ≈ 0，两高张 +9.7，暗三条 +22.6。

### 3.4 求解器与启发式共用范围（v0.18.0）

避免「转牌按均衡打、河牌按启发式打」的割裂。同时做了 8 万手定论测量。

### 3.5 剥削层（v0.19.0）

`src/ai/exploit.ts`：公开统计 → 价值线 / 诈唬率 / 跟注线。
配对审计（500 手/臂）：对弃牌怪 +17.7、对紧手 +21.8、对跟注站 +270、对疯子 +375.7。

**关键洞察**（写进代码注释）：**跟注阈值不能用弃牌率推**。
跟注站弃牌率低意味着「他爱跟」，不是「他很少诈唬」——这两件事方向相反。

### 3.6 翻前整体换成 EV 引擎（v0.20 → v0.21）

v0.20 只修了「面对大幅加注」一个分支，但病根更深：整套翻前是**三层阈值表**
（入池线 / 加注线 / 3-bet 线）+ 随机混合系数。三个结构性缺陷：

1. 跟注额不参与决策；
2. 位置只影响阈值高低，不影响「这手牌在这里值多少钱」；
3. 加注只看牌力，不看弃牌率——对手从不弃牌时加注毫无意义。

v0.21 全部删掉，换成 `src/ai/preflopEv.ts`：逐动作算 EV，取最大。

### 3.7 打包三件套（v0.22）

- **Windows**：Electron + NSIS 一键安装包（`electron-builder.yml`）；
- **跨平台**：单文件 HTML（`vite.config.single.ts` + `build-single.mjs`），双击即玩；
- **安卓**：Capacitor + Gradle（`scripts/build-apk.mjs`）。

三个坑记在这里，别再踩：
1. `electronDist` 必须指向 `node_modules/electron/dist`，否则打包时会去 GitHub 下载，
   在需要代理的网络下**静默卡死**；
2. Node 的 `fetch` 和 `got` **都不认 `http_proxy`**，Electron 二进制要用 `ELECTRON_MIRROR` 或本地缓存；
3. `createDesktopShortcut` 必须是 `always`，`true` 在静默安装下不建桌面图标。

**另外**：本机环境变量里有 `ELECTRON_RUN_AS_NODE=1`，所有 electron 命令都要
`env -u ELECTRON_RUN_AS_NODE` 前缀，否则 `app` 是 undefined。

### 3.8 手机端布局（v0.22，返工两次）

四条不能回退的约束（`AGENTS.md` 第 10 条）：
1. 行牌提示条在手机端必须**随文档流**（不能 `position: fixed` 盖住工具栏）；
2. 中央 `.table-status` 在手机端**隐藏**（与底部操作区完全重复，且压在座位上）；
3. 牌桌椭圆必须**窄于座位环**，否则座位整块压在绿色桌面上；
4. 公共牌 `clamp(30px, 7.4vw, 40px)`。

**返工原因**：第一次只改了自己臆想的布局，没有截图对比。用户第二次反馈「牌面显示不全、
花色盖住字母」后，才用 `npm run shot:mobile` 真机尺寸截图复现并修对。
牌面字号改成按牌宽比例（`calc(var(--card-w) * 0.34)`），小牌隐藏中央花色。

### 3.9 对手范围模型重做（v0.23.0）——这一版最实在

**先修测试台**：旧的 `scripts/_cmp.ts` 每手都 `createTable` 一次，`statsRaw` 永远是空的。
也就是说机器人**从来没有机会观察到「这家伙每手都全下」**，读人层被整段屏蔽。
换成 `scripts/session.ts`（同一张桌子连打 N 手、每手重置 50BB）后，
v0.22 判定的「专家对全下怪 +63.8」实际是 +323.8。

据此发现三个真缺陷：
1. **跟注全下之后没有翻后，权益实现率必须是 1**（旧按 OOP 给 0.70，把价值砍掉三成）；
2. `estimateRaiserRange` 只看「押了多少筹码」，不看对手多爱加注；
3. **`pfrRate` 的分母含「没轮到动作」的手**，一个每轮到我加注就推的疯子 PFR 也只有 75%。
   新增 `pfrOpportunityRate = pfr / pfrOpps`。

实测（对 v0.3.0）：**统一口径的最新数字见 §1.4.4 的表**，这里不重复贴，
避免出现两套口径（早期那次是 400 手 × 2 座位、且带蒙特卡洛上限，与现在的口径不可比）。
一句话：v0.23.0 之后，专家档和挑战档在三个固定对手上都不低于 v0.3.0。

### 3.10 加细抽象与加细树（v0.24.0）——三个负面结论

你要求「往加细抽象 + 加细树推进，争取启用 A/B」。做了，但结论和直觉相反：

| 改动 | 测法 | 结果 | 决定 |
| --- | --- | ---: | --- |
| 翻前桶 24→48 | 可利用度 | 0.0312 → **0.0341**（还慢 3.7 倍） | 维持 24 |
| 转牌价值网络扩容 | 留出集 R² | 0.378 → **0.552** | ✅ 采用 |
| 翻牌蓝图（修完两个 bug） | 配对消融 / 新旧对打 | −8.8 / −41.4 | 关闭 |
| 转河组合 24→40 | 新旧对打 4000 局 | **−44.5** [−104, 15] | 维持 24 |

**为什么「加细」没带来「更强」**：抽象细度和收敛程度是一对 trade-off。
翻前 48 桶把信息集变成 4 倍，同迭代数下反而收敛更差。
转河 40 组合更精确，但对手不按均衡打时，更精确的均衡解不是更好的应对。

### 3.11 求解器被误关的两个 bug（v0.25.0）

起因是 v0.24.0 测出「挑战 vs 专家 −38.3」。我没有去调参，而是先统计**引擎命中率**：

| 引擎 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 转河 CFR+ | **3.2%** | **14.2%** |
| 河牌单街求解 | 0% | 3.1% |
| 启发式兜底 | 52.4% | 39.4% |

挑战档的全部卖点就是「专家档 + 求解器」，而求解器只覆盖 3.2% 的决策。两个 bug：

1. **`observedPassiveLine` 把 `[check, check]` 当成跟注站**。单挑大盲本来就常过牌，
   于是大部分转牌决策跳过求解器。改成要求「至少跟过一次」。
2. **`solverShouldYield` 复用了 `hasStrongExploitRead`**，而它把「弃牌率 ≥ 70%」也算强读。
   但对手越爱弃牌，均衡解器的诈唬越有效——这条判据对**任何正常对手**都会触发。
   拆成两个概念：「该开剥削层」（含过度弃牌）vs「该放弃求解器」（只有不弃牌才算）。

## 4. 亲自下场打牌发现的问题

### 4.1 已修

- **推理日志自相矛盾**：日志写「加注 EV 2 → 弃牌」（加注更高却弃牌）。
  根因是挑战档决策噪声 8 筹码（0.4BB）足以翻掉 +2 的正期望决策。已压到 3，并加注「决策噪声」说明。
- **翻前 EV 引擎在 0 EV 附近做决策**：噪声直接决定动作。同上。

### 4.2 未修（留给接手者）

**3-bet 过宽 + 翻后直接放弃**：机器人（小雅）用 Q5s 3-bet 到 239 筹码（约 12BB），
翻牌 9s2hKd 后三条街全部过牌，白送 239。

这是最容易被人类剥削的模式——**只要跟注它的 3-bet，翻后它从不继续施压**。
未修的原因：需要翻后引擎知道「我刚 3-bet 过，我的范围很强」，
属于范围模型与多街一致性问题，不是翻前能解决的。**这是我认为最值得优先修的实战漏洞。**

## 6. 已知问题清单（按严重程度）

### 6.1 结构性（最难，也最值得做）

**翻牌仍然是 100% 启发式。** 实测（`_diag-engines`，挑战 vs 专家）：
翻牌决策占全部决策的 **22.8%**，而其中 **100% 走启发式**，且两档跑的是**同一套代码**——
这是「挑战档无法吊打专家档」的根本原因。
（挑战档整体启发式兜底占 39.4%，剩下那部分是其他街没触发求解器的场合。）翻牌蓝图（A 路线）做了三版、修了两个真 bug，实测仍是负贡献，已结案：
**「桶抽象 + 价值网络叶子」这套近似本身打不过启发式。**

### 6.2 能力缺口

- 多人（3 人以上）不套单挑解，走启发式 + 谨慎系数；
- 翻前树只有 2 个加注尺度，4-bet 以上不覆盖；
- 读计时 / 读下注细节是统计启发式，不是模型。

### 6.3 我自己犯过的错（写下来防止重犯）

**错误一：把 1400 局的 −38.3 当成结论。**
我在 v0.24.0 的交付里写「挑战档打不过专家档」，你据此要求必须解决。
用 5000 局重测后发现：**v0.24.0 本来就是 +23.4**，那个负号是 SE≈48 的噪声。
教训：**任何「A 比 B 强/弱」的结论，样本量必须按效应量反推**，
17.5BB 的单手标准差下，要分辨 20 BB/100 需要约 4.8 万局。

**错误二：测试台给两边都传 `maxIterations: 800`。**
`resolveIterations` 取 `min(profile.mcIterations, maxIterations)`，
而挑战档是 30000、专家档 20000——这个参数把挑战档的计算优势整个抹掉，
**导致所有历史基准都在低估挑战档**。真实游戏（`useAiDriver`）对本地 AI 不传这个参数。

**错误三：翻牌蓝图的叶子喂错了输入。**
旧实现把「手牌桶下标」当「成牌强度」、听牌恒填 0 喂给价值网络，
而网络是用真实底牌训练的。更严重的是**只喂了 SB 的牌**，BB 的手牌完全不影响估值，
于是 BB 对 16 个手牌桶的策略一模一样。修完后策略变成教科书式极化，
但仍然打不过启发式——**修对了 bug 不等于修对了方向**。

### 6.4 待办小事

- `HU_SB_PREFLOP`（单挑 SB 放宽开池）是**死代码**：翻前蓝图会覆盖它，实测开关无差别；
- `scripts/_diag-*.ts` 是诊断脚本，没有测试覆盖，改动核心逻辑时可能失效。

## 7. 下一步方向（按优先级，含验收标准）

### P0：把 +21.9 测到显著

**为什么先做这个**：现在连「挑战档是否真的比专家档强」都说不清，谈「吊打」没有基础。

**做法**：`HANDS=12000 npx tsx scripts/head2head.ts`（2.4 万局，单机约 2 小时）。
**验收**：CI 下界 > 0。
**如果 CI 下界仍 ≤ 0**：说明 +22 是噪声，挑战档需要重新设计，而不是继续微调。

### P1：把翻牌纳入求解（唯一能拉开档次的路径）

**技术方案**（我评估过，可行但工作量大）：

1. **离线预计算**：对「翻牌纹理 × 手牌桶」预计算两街权益矩阵，存成数据文件；
2. **在线求解**：扩展 `subgame.ts` 支持翻牌——把 `terminalShowdown` 换成
   「转牌起点」的叶子估值，用 `turnValue.ts` 的价值网络；
3. **成本控制**：目标单次决策 ≤ 300ms（当前转河求解 181ms）。

**必须先解决的问题**：价值网络当前 R² 0.552、MAE 0.173 个底池，**还撑不起一个可靠的翻牌解**。
需要先把 R² 推到 0.7 以上（更多样本 + 更细特征 + 更大的网络）。

**验收**：`head2head` 里挑战 vs 专家 ≥ +50 BB/100，CI 下界 > 0。

### P2：修 3-bet 后的多街一致性（§4.2）

**做法**：让翻后引擎知道「我这手是 3-bet 底池」，范围与尺度相应调整。
**验收**：`play-as-human` 重放那手 Q5s，翻后不再三条街全过牌。

### P3：产品层选择（需要你拍板）

如果产品上必须让玩家**明显感觉**宗师比专家强，有两条路：

- **A（真变强）**：走 P1，工作量大但真实；
- **B（改产品定义）**：把专家档定位成「无求解器的强启发式」，
  去掉蓝图范围模型、保留更高失误率，让两档按**能力分层**而不是「专家 + 插件」分层。
  改动快，但这是产品决策，不是技术决策。

**我的建议**：先做 P0 确认现状，再评估 P1 的工期。如果等不起，B 是诚实的替代方案——
但要在 README 里写清楚，不能假装是「变强了」。
